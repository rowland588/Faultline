# Luna: full capability and functional audit — 24 November 2026

Connector readiness and follow-up intelligence fixes are recorded in `docs/LUNA-CONNECTOR-INTELLIGENCE-20261124.md`.

## Verdict

Luna is a useful, unusually broad **personal** AI colleague for Faultline. She can read and work across line records, studies, problems, actions, documents and connected workbooks; run app calculations; prepare reports and presentations; and propose record changes for confirmation. The core tool boundary is sound in code: registered operations and model schemas match 133 to 133, figures are computed by Faultline, and writes use cards or authorised job scope. This is a capability inventory, **not** proof that all 133 operations succeed in real use.

The biggest quality gap is proof. Most complete journeys have fixture browser coverage, while current real-model reliability and end-to-end live integrations are sparsely measured. The standing briefings cloud tick was actually broken in production; it is repaired and answered HTTP 200, but there were zero enabled schedules to demonstrate a delivered briefing. Live and repository Edge Function source had diverged. The same sort of source drift could hide other faults.

## Live measurements and incident

Read-only production usage over the preceding seven days showed **28** ordinary colleague gateway requests, all transport `ok`, with per-call p50 2.394 s, p90 6.589 s and $4.86 total. There were **182** colleague-check requests, all transport `ok`, p50 3.184 s, p90 5.455 s and $8.26 total. All 28 ordinary calls used `tools_mode=all` and `effort=low`; 15 ended with a tool call, 13 with a final answer. `ok` measures the gateway returning, **not** answer correctness, an entire job's latency, or voice latency. Sending every tool schema every turn increases context cost and selection burden; tool search exists but is not the live default or evaluated head to head.

The latest documented real-model exams were limited single runs (job 13/14 on 23 November, workbook 10/10 on 22 November). A repeated job pass was blocked by the existing $3/day checking allowance. Older bagger/packing investigations may have stale grades or scoring; do not quote them as current reliability. This audit deliberately did not consume additional model-check budget.

The past 24-hour cron history showed 96/96 successful Luna job ticks, 24/24 keep-up ticks and 96/96 ingest pulls. **Standing briefings had 4/4 failed ticks** because the cron command built a null URL from a missing `project_url` Vault secret. `standing_job_keys` was still `SET-ME`. The original repository file showed a weekly cron and an older counting-only Edge Function, whereas live production had an hourly cron and a newer function that marks and pushes due jobs. Repairs:

1. `supabase/20261124_a_standing_jobs_cron_repair.sql` generated a random request key and put the project endpoint directly in the cron command.
2. `supabase/20261124_b_standing_jobs_hourly.sql` restored hourly ticks so daily and weekday schedules are not missed.
3. The deployed `standing-job` v3 source was copied back to `supabase/functions/standing-job/index.ts` to remove repository drift.

Both migrations were applied to production. Readback showed active cron `5 * * * *`, a non-placeholder key and the correct URL. A manual `pg_net` request using the stored key returned **HTTP 200**: `{enabled:0,marked:0,pushed:0}`. The next scheduled tick at **22:05 UTC succeeded** in `cron.job_run_details`, following the 21:05 failure. The request path is repaired; it cannot prove a due job is marked or pushed because none existed.

## Priority work

1. **Prove a real scheduled briefing and notification.** Create an opt-in test schedule owned by the user, check the cloud mark/push, open Luna to verify the briefing, and verify Outlook send only with the user's intended recipient. Add error/status visibility to the Schedules card. Today the UI can imply more autonomy than the full path has proved.
2. **Verify voice on Android Chrome and the installed app.** The hidden desktop Talk control was fixed and the fixture journey passed. Confirm real microphone permission, recognition restart, device TTS and a phone-size viewport. Keep a typed alternative visible when recognition is unavailable.
3. **Measure answer correctness and action completion, not merely HTTP success.** Run a small fixed evaluation on current production code across workbook, line, action, job and report tasks; grade correct source, exact figure, omissions, permission and completed action. Repeat enough to expose flakiness, within an explicit budget.
4. **Close the report data loop.** Every visual should expose the exact data table and source rows; indicate source age and missing values. A dashboard should refresh from current records on open and show a visible “as of” date. A frozen report should remain clearly a saved snapshot.
5. **Reduce model tool load with measured selection.** Compare all 133 schemas against the existing search modes on the same tasks for correctness, steps, latency and cost before changing the default. Keep required action tools discoverable.
6. **Make unattended delivery honest and complete.** The server currently queues a due marker and push; building the digest and using Outlook credentials remain device work. Design server-readable sources and explicit delegated sending authority before promising delivery while closed.
7. **Keep deployed Edge Functions and repo in lockstep.** A release check should compare deployed function version/hash or deploy from the repository, then read back cron and table state after every migration.

## New opportunities beyond the current plan

- **Source health contract.** For every answer, Luna could know the last successful source read, whether expected columns changed, missing records, and staleness. She would say when a source is old before offering an action. This is more useful for personal operations than a generic confidence score.
- **Action outcome coach.** When a tool result or Luna finding creates an action, capture the expected metric and review date. At the review, compare the real metric with the baseline and ask whether the change held. This links tools, problems, Luna and Actions into one operational loop without adding a new top-level page.
- **Decision rehearsal.** Luna could combine existing capacity, staffing and loss tools into a what-if comparison, state assumptions, show ranges and explain which missing input changes the decision. Individual what-if tools exist; cross-tool orchestration is the new capability.
- **Evidence drill through from visuals.** Tap a chart point to see the exact source records, row references and calculation used, then open the relevant line or workbook. This makes an impressive presentation inspectable in a real meeting.
- **Work queue based on exceptions.** A single Luna view could group stale data, unreviewed actions, due checks and failed schedules into a short “needs you” list, each with one clear next step. Keep the app's existing records as the source of truth.

This audit applies to the current personal-use product. Multi-tenant SaaS administration, billing and organisation roles are not a prerequisite for these improvements.
